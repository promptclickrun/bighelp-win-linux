# Protected repository evidence

2026-10-16. Main-process-only adapter; no new dependencies. `createProtectedRepository({ directory, protection, platform })` accepts an injected Electron-safeStorage-compatible provider. Reads return `{ revision, value } | null`; writes accept bounded unknown JSON and an expected revision (`null` means absent). Removes use the same comparison. Call `close()` at orderly shutdown.

The adapter rejects unavailable encryption and Linux `basic_text` (also missing backend inspection), checks protection again per operation, and never writes plaintext. SHA-256 filenames hide bounded opaque keys; the encrypted versioned envelope binds key and revision. Limits: 1 MiB complete plaintext envelope (value size alone may fit but be rejected before encryption if metadata exceeds this limit), 1 MiB + 64 KiB ciphertext, 64 JSON levels, 100,000 JSON nodes, 1,024-byte well-formed keys. Unsupported/corrupt envelopes block mutation and remain intact. Reads bound allocation and file size before decrypting, then bound plaintext before parsing. Symlinks/nonregular files and symlink directory components are rejected.

Writes snapshot input, serialize CAS operations, create exclusive random 0600 temporary files, flush the file, then atomically rename within the directory. On POSIX, successful creation flushes newly created directory entries and lock metadata; writes and removals flush the repository directory after rename/unlink and before resolving. Failures before rename leave the old committed value intact. A directory flush failure after rename/unlink reports uncertain durability and blocks all further operations until close/reopen; it does not pretend the committed entry stayed unchanged or encourage automatic retries. Removal touches only the requested record; temporary leftovers are never adopted or broadly cleaned. A lifetime exclusive directory lock prevents another cooperating instance/process from opening the same repository. A dead PID (`ESRCH` only) permits reclamation: claim a subdirectory inside the stale lock, then recheck directory inode, PID, nonce and liveness before removing it. Concurrent reclaimers cannot remove a new owner's lock. Live/reused PIDs, permission errors, missing/malformed metadata and abandoned reclamation claims fail closed; exceptional incomplete-lock recovery requires confirming no owner remains before removing that exact lock.

Synthetic Linux/container evidence uses real temporary files and injected AES-GCM, not the OS secret store. Tests cover reload, concurrent CAS, separate-process contention, SIGKILL of a lock owner and successful reopen, protection refusal, ciphertext/plaintext absence, encrypted identity substitution, corrupted/oversized files, file mode, symlink/nonregular rejection, unsupported schema preservation, encryption failure, fault-injected directory-flush failures after write/removal, observed POSIX directory sync ordering, interrupted temporary-file leftovers, immutable queued snapshots, JSON limits (including roundtrips at node/depth limits and near the complete envelope byte limit), and scoped deletion. Tests were written before the implementation; the initial run failed because the new module was absent.

Limitations: no actual Windows DPAPI or Linux Secret Service qualification, Windows ACL/reparse-point assessment, physical power-loss or injected disk-full/rename-failure testing. POSIX file and directory fsync ordering is verified with real handles and injected sync failures; physical power-loss behavior and filesystem/device guarantees remain unqualified. Windows uses atomic replacement plus file sync for process-interruption protection; portable Node cannot flush directory handles there, so metadata durability across power loss remains an explicit release qualification gap. Development remains usable on Windows, without claiming POSIX directory durability. The repository must live in an app-private directory with trusted ancestors: portable Node pathname checks cannot defeat a malicious local process concurrently replacing ancestor directories. File mode 0600 is not proof of Windows ACL isolation. Decryption providers allocate plaintext internally before the adapter can inspect it; safeStorage remains the trusted protection boundary. JS does not guarantee zeroization. Encryption protects confidentiality at rest; local rollback/deletion by a filesystem writer is not detected. Revision numbers restart after an explicitly removed record is recreated.

Verification: `npm test` and `npm run typecheck` pass. These are synthetic/container checks, not packaged-app or physical-machine evidence.

Security-review follow-up: read validation now applies node/depth budgets to the value alone, matching writes; envelope metadata has a strict four-field shape and its own byte/version/key/revision checks. Previously a value exactly at the allowed node/depth boundary could commit but fail to read because envelope metadata consumed the same budget. Regression tests reproduced this failure before the fix.
