# Unsigned portable development packaging

Date: 2026-10-16. These artifacts are development builds, not installers or releases.

## Beta layout (0.9.0-beta.1)

Packages are now `artifacts/bighelp-beta-<package.json version>-<os>-x64` with a `.tar.gz` or `.zip` and its `.sha256`. Still unsigned and portable: no installer, signing, publishing or updates. Changes from the development layout described below:

- The runtime executable is renamed to `bighelp` / `bighelp.exe`. Its embedded Windows file icon and version resource are still Electron's; changing them needs a resource editor, which is a new dependency. The window, taskbar and tray icons come from `resources/app/icons/` (generated by `scripts/desktop/icons.mjs`, Node built-ins only).
- The app identity is `bighelp`, version from `package.json`, `desktopName` `bighelp.desktop`. Packaged builds use the `bighelp` userData folder and, on Windows, the AppUserModelID `bighelp`. Development runs keep `bighelp-desktop-dev` and never register a login item.
- `README.txt` replaces `DEVELOPMENT.txt`: the unsigned beta, SmartScreen "More info → Run anyway", the Linux keyring and sandbox requirements, tray and notification behaviour, where data lives, and how to uninstall.
- Linux adds `bighelp.desktop` (a template) and `install-desktop-entry.sh`, which installs or removes a menu entry for the current user with the folder's escaped path.
- `scripts/desktop/package-layout.mjs` checks the assembled folder before archiving: renamed executable present and executable, old name absent, README and notices present, app identity and version, and SHA256SUMS covering every file.

Evidence so far (macOS development host, 2026-10-16; not target qualification): `tests/desktop-package-layout.test.mjs` assembles synthetic Linux and Windows runtimes and runs the menu entry script with an awkward path. The real pinned Electron 44.7.2 Linux and Windows runtimes were downloaded, checksum-verified and assembled into the beta layout with the package code on macOS (91 checksummed Linux files; executable modes retained in the tar headers). Nothing was launched from those packages. Packaged launch, sandbox, tray, toast and autostart behaviour on Windows 11 and Ubuntu 24.04 still need the CI smoke and physical-machine checks.

Current integrated verification and downloadable native artifacts are tracked in [development build qualification](development-build-qualification.md). The local `c877ee2` package includes all 15 bundled dependency notices, passes all 82 file hashes plus its archive hash, and passes 20/20 packaged smoke checks with the OS sandbox enabled. Older results below describe their original milestones.

`node scripts/desktop/package.mjs [linux|win32] [x64]` builds production resources, downloads the pinned Electron runtime with `@electron/get`, independently verifies its archive against the checksums bundled with the locked Electron dependency, and assembles a portable directory under ignored `artifacts/`. Run on the target OS. Other operating systems and architectures fail before building or downloading. No dependencies were added.

The runtime retains its original executable name (`electron` or `electron.exe`). Its packaged application has the private identity `bighelp-development`, version `0.0.0`, and entry point `resources/app/main.cjs`. Only the four application bundle files, optional esbuild license companions, and required `THIRD_PARTY_NOTICES.txt` / `THIRD_PARTY_NOTICES.json` enter application resources. Source, fixtures, environment files, source maps, repositories, and credentials are not copied. Symlinks and special source entries are rejected. Electron's default application is removed. Project LICENSE/NOTICE and Electron/Chromium licenses are retained. SHA256SUMS covers every regular artifact file except itself, including both npm notice files; a separate SHA256 accompanies the tar.gz or zip. SHA256 detects corruption; it is not a signing identity.

The build derives npm attribution from the main, preload, and renderer esbuild input graphs, including transitive/scoped packages and separate nested installations. It copies complete license and notice texts from each package root and the directories containing bundled inputs; unrelated package trees are not traversed or copied. The text file contains the full notices. The JSON records each package name/version, relative installed package path, package.json SHA256, inputs by bundle, full notice texts, original notice paths/hashes, and the text file's SHA256. The package validator requires both files, verifies individual notice hashes and the complete text rendering, and rejects missing full licenses. Legal comments pointing to absent root licenses are not treated as sufficient attribution.

One explicit reconstruction is necessary: the locked `@react-native/normalize-colors@0.74.89` npm package omits the root LICENSE referenced by its `index.js` header. Its package metadata declares MIT and its source header names Meta Platforms, Inc. and affiliates. The build verifies those exact declarations and includes the matching complete Meta MIT license from installed `react@19.3.1/LICENSE` (SHA256 `da6d3703ed11cbe42bd212c725957c98da23cbff1998c05fa4b3d976d1a58e93`). This exception is pinned to both versions and that full license hash. The JSON retains the normalize-colors source-header excerpt and source hash, plus the donor version, path, package.json hash and license hash. The text file identifies this as a reconstruction from React, not a file originally shipped by normalize-colors. Changed declarations, versions or donor text fail the build; other missing full licenses have no fallback.

Linux archives use system tar; Windows archives use PowerShell Compress-Archive. There is no installer, signing, publishing, auto-update feed, ARM build, or reproducible-byte archive claim. The Electron executable and OS sandbox configuration are retained: the package never sets `--no-sandbox`, changes chrome-sandbox ownership, or relaxes OS settings. Linux operators must provide a supported sandbox configuration and desktop environment; OS sandbox setup on ephemeral CI runners belongs to the runner administrator. Launching from a root container is not qualification.

The platform workflow targets Ubuntu 24.04 x64 and Windows Server 2022 x64 hosted runners with Node 24. It installs the lockfile, explicitly verifies esbuild and fetches Electron, runs tests and strict compilation, builds production resources, packages, and uploads short-lived unsigned development artifacts. Passing this workflow qualifies build assembly on these runners only. It does not qualify Windows 10/11, Linux distributions, Wayland/X11, accessibility, audio, notifications, OS key stores, physical hardware, or production distribution. Packaged launch and sandbox smoke evidence must be recorded separately.
